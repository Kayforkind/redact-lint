# Where redact-lint stands, and what "complete" would take

Written after the 0.2.2 release, action and sweep: measured, not estimated.
The plan below was followed; see [Status at 0.3.1](#status-at-031) at the end for
what landed and what did not.

## Score: 6 / 10

A working, tested, published tool with a real thesis — and an accuracy claim
nobody has measured yet.

| Dimension | Score | Evidence |
| --- | --- | --- |
| Core idea | 9 | Paint order is the right discriminator; no mainstream tool does this check |
| Engineering & release | 9 | 28 tests, 4 CI jobs, OIDC provenance, semver tags, no secrets |
| Detection coverage | 5 | Painted fills only; image covers, annotations, form fields, invisible text all unhandled |
| Real-world validation | 3 | Every fixture is generated by pdf-lib; no corpus, no precision/recall |
| Adoption ergonomics | 5 | No waivers, no baseline, no SARIF, no TypeScript types |
| Documentation | 7 | Strong README and launch post; no changelog, no algorithm page, no troubleshooting |
| Distribution | 7 | npm, composite action, weekly sweep; single ecosystem |
| Governance | 3 | No SECURITY.md, CONTRIBUTING, issue templates, or GitHub Releases |
| Performance | 8 | 100 pages / 4,000 runs in 922 ms, +58 MB RSS; nothing tested at 1,000 pages |

The gap between 9 for engineering and 6 overall is the honest story: this is a
well-built thing whose central promise — "trust this verdict" — is untested on
documents the tool did not generate.

## What "complete" means

Complete = **a stranger can adopt it without hitting an unknown unknown.** Concretely:

1. Accuracy is measured on a public corpus and published, per leak class and
   per PDF producer.
2. The four leak classes that actually occur are covered: painted fill (done),
   image cover, annotation/form-field text, invisible text.
3. Encrypted PDFs behave explicitly — opened when an empty password works,
   refused with a clear message and exit code when not.
4. False positives can be waived with a recorded reason, so one bad finding
   does not block a team from adopting the tool.
5. It runs where work happens: GitHub Actions (done), any CI via CLI (done),
   pre-commit; the library is typed for TypeScript consumers.
6. Governance exists: security policy plus threat model, contributing guide,
   changelog, GitHub Releases, issue templates.
7. CI proves the shipped artifact on Linux, macOS and Windows, and a
   performance budget guards large documents.

## Plan

Sequenced by risk, not by appeal: measure first, then widen coverage, then
remove adoption friction. Building features on an unmeasured detector just
produces confident wrong answers.

### Phase 0 — Measure the detector (2–3 days)

The single most valuable work available, and the reason the score is not higher.

- `bench/corpus.json` manifest + `bench/run.mjs` harness; `BENCHMARK.md` output.
- 60 documents with ground truth: 20 from real producers (Chromium print,
  LibreOffice, Word, Google Docs), 10 LaTeX, 10 scanned/OCR, 10 government
  forms, 10 adversarial edge cases (rotated, clipped, nested XObjects,
  two-column, CJK, right-to-left).
- Metrics: precision, recall, F1 per class, broken down by producer; runtime.
- Fix the top five failure causes the corpus exposes.

**Acceptance:** numbers in `BENCHMARK.md` reproducible from the repo; no crash
on the corpus; failures triaged into issues with fixtures.

**Unlocks:** 6 → 7.5. A published error rate is what turns a demo into a tool.

### Phase 1 — Cover the leaks that matter (5–6 days)

- **Image covers:** `paintImageXObject` placed after text, transform bbox over
  a text box → report as `image-cover` with severity "unverifiable by text
  extraction", not "leak".
- **Annotations and form fields:** `getAnnotations()`, field values,
  appearance streams; text there is extractable regardless of any rectangle.
- **Invisible text:** render mode 3, text painted in the background colour,
  clipped-away runs.
- **Encrypted PDFs:** attempt empty-password open; otherwise exit `3` with
  "encrypted, provide --password" and support `--password`.

**Acceptance:** each class has ≥3 fixtures and tests; benchmark delta recorded;
README's "what it does not catch" shrinks to what is genuinely out of scope.

**Unlocks:** 7.5 → 8.5.

### Phase 2 — Remove adoption friction (3–4 days)

- `.redactlintignore`: path glob + optional page + **required reason string**,
  plus `--baseline` to accept current findings.
- Action input `ignore-file`; document the waiver workflow.
- SARIF output (`--format sarif`) with a `upload-sarif` example, so findings
  land in code scanning where reviewers already are.
- `pre-commit-hooks.yaml` so the check exists before the commit.
- Type declarations for the library export (`analyzePdf`, result types), with a
  `tsc` consumer sample in CI.

**Acceptance:** a known false positive is waived end-to-end by a test; SARIF
validates against the schema; a sample TS project compiles against the package.

**Unlocks:** 8.5 → 9.

### Phase 3 — Trust surface (2–3 days)

- `SECURITY.md` with a threat model: pdfjs parses hostile input, so document
  limits (page count, byte size, timeout) and how to report a parser bug.
- `CONTRIBUTING.md`, issue templates, `CHANGELOG.md`.
- Release workflow creates a GitHub Release with notes from the changelog.
- CI matrix: `ubuntu`, `macos`, `windows`; performance budget test
  (200 pages under a generous ceiling) to catch accidental quadratic work.

**Acceptance:** every tag has a Release page; three-OS matrix green; changelog
covers 0.1.0 → current.

### Phase 4 — Reach (optional, 2–3 days, only after 0–3)

Pick one, based on where interest actually comes from: a docs site with the
algorithm explained, a Docker image, or a Homebrew formula.

**Explicit non-goals:** a hosted upload service (local-first is the product),
OCR/redaction verification of pixels (different tool), native ports per CI.

## Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Real PDFs behave differently from fixtures | High — core promise | Phase 0 before anything else; publish the failures too |
| False positives block adoption | High | Phase 2 waivers; thresholds tuned on the corpus, not guesses |
| pdfjs parser is an attack surface | Medium | Explicit size/time limits, security policy, dependency pinning |
| Single maintainer | Medium | Contributing guide, small focused issues, reproducible benchmark |
| Scope creep toward a redaction *editor* | Medium | Non-goals list above; this is a checker |

## Status at 0.3.1

**Score: 8.5 / 10.** Up from 6: coverage, adoption friction, governance and the
first real-producer evidence are done. The ceiling is still evidence, but it is
now a smaller gap. `BENCHMARK.md` reports 100% recall and zero false positives
on 25 documents, 8 of which were exported by Chrome 156, Word 16 and ReportLab
5.0 and committed byte-for-byte. That run was worth doing for its own sake: the
Word documents exposed a run-to-operator pairing bug that produced four false
positives on a clean shaded table, which 0.3.1 fixes.

| Phase | State | What shipped |
| --- | --- | --- |
| 1 Coverage | Done | `image-cover` (bitmaps and stencil masks, page-sized images excluded), encrypted PDFs via `--password` with exit `3`, `--annotations` for form fields and annotations, page-area guard for scans |
| 0 Measure | Partial | 25 documents: 17 synthetic across pdf-lib, PDFKit and a hand-written content stream, plus 8 committed PDFs exported by Chrome 156, Word 16 and ReportLab 5.0, with recall per class and per producer, `BENCHMARK.md`, and `npm run bench:check` floors. Still missing: LibreOffice, LaTeX, Acrobat and a real 60-document sample. The committed corpus is fixtures, not published filings |
| 2 Adopt | Done, except `--baseline` | `.redactlintignore` with mandatory reasons and per-page rules, `--ignore-file`, SARIF 2.1.0 via `--sarif`, pre-commit hook manifest, TypeScript declarations checked by `tsc` against a consumer sample. `--baseline` (accept every current finding so only new ones fail) was not built: per-file and per-page waivers already cover the adoption case, and a baseline file is easier to leave stale than a waiver with a reason |
| 3 Trust | Done | `SECURITY.md` with threat model, `CONTRIBUTING.md`, `CHANGELOG.md`, issue forms, PR template, GitHub Releases from `release.yml`, macOS/Windows CI matrix, 200-page performance budget in CI |
| 4 Reach | Not started | Optional by design; no evidence yet of where demand is |

### What still separates 8.5 from 10

1. **A wider real corpus.** Word, Chrome and ReportLab now have committed
   output. LibreOffice, LaTeX, Acrobat and Google Docs do not, and eight
   fixtures are not sixty real filings with ground truth. Add documents to
   `bench/real/manifest.json`; `bench:check` scores them on the next run.
2. **Invisible text** (render mode 3, background-coloured text) is still a
   different check that does not exist.
3. **Distribution beyond npm.** A Docker image or Homebrew formula, once there
   is a reason to pick one.

The order has not changed: corpus first. The Word run just demonstrated why —
two documents, one real bug, caught before a user could hit it.
